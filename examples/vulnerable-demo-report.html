M3 · Insecure Authentication/Authorization

Weak identification of the user or of the caller of an app component, letting an attacker reach functionality they should not.
High Exported activity with no permission check (2) MAN-EXPORTED-ACTIVITY
M3 Insecure Authentication/Authorization CWE-926MASVS-PLATFORM confidence: High analyzer: manifest
What was found
2 activity component(s) are exported without an `android:permission` attribute. Any other app installed on the device — including one the user installed by accident — can start them directly and supply arbitrary Intent extras. If the component performs a privileged action, or trusts data from the Intent, that is a way in that bypasses the app's own UI and whatever authentication it does.
How to fix it

High WebView exposes a Java object to page JavaScript WEB-JS-INTERFACE
M4 Insufficient Input/Output Validation CWE-749MASVS-PLATFORM confidence: High analyzer: webview
What was found
`addJavascriptInterface` binds a Java object into the WebView's JavaScript context. Whatever HTML the WebView ends up displaying — including a page reached through a redirect, an injected iframe, or an ad network — can call the annotated methods on that object with arguments of its choosing. On API 17+ only @JavascriptInterface-annotated methods are exposed, so the risk is bounded by what those methods do — but each one is an entry point callable by untrusted page content.
How to fix it
Remove the bridge if the page content does not need it. If it does: load only content you control over HTTPS, keep the bridge object as small as possible, validate every argument, and never expose methods that touch the filesystem, credentials or other components. Prefer `WebMessagePort` for structured, origin-checked messaging.

Critical TrustManager accepts every certificate NET-TRUSTMANAGER-ALLOW-ALL
M5 Insecure Communication CWE-295MASVS-NETWORK confidence: High analyzer: network
What was found
A class implementing `X509TrustManager` has an empty `checkServerTrusted`. An empty implementation raises no exception, which is how the API says "this certificate is valid" — so the app accepts any certificate from any server, including a self-signed one an attacker generates. TLS still encrypts the connection, but to whoever intercepted it: the confidentiality and authentication guarantees are both gone, silently.
How to fix it
Delete the custom TrustManager and use the platform default. If a private CA must be trusted, add it as a trust anchor in the network security config instead of writing validation code. Never ship the permissive version that was added to make a staging certificate work.

Low No certificate pinning was found NET-NO-PINNING
M5 Insecure Communication CWE-295MASVS-NETWORK confidence: Medium analyzer: network
What was found
No certificate or public-key pinning implementation was found (no OkHttp CertificatePinner, TrustKit, or `<pin-set>` in a network security config). Without pinning, the app trusts every CA in the system store, so a mis-issued or compromised CA certificate — or a CA an attacker can coerce — is enough to intercept traffic. Reported as an absent hardening measure, not a defect: pinning carries real operational risk if certificate rotation is not automated, and is not appropriate for every app.
How to fix it
For an app handling authentication or financial data, pin to the public key (not the leaf certificate) of your own backends, include a backup pin, and make sure the rotation process is tested before shipping — a pin that expires bricks the app in the field.

How the risk score is calculated
Each finding contributes its severity weight (Critical 10, High 7, Medium 4, Low 1.5, Info 0) multiplied by a confidence factor (High 1.0, Medium 0.7, Low 0.4). A single rule contributes at most three times its unit weight, so one noisy rule cannot dominate. The total is mapped to 0-100 through 100 x (1 - e^(-total/30)), which saturates: the score is a communication device for ordering and triage, not a measurement of real-world risk.
